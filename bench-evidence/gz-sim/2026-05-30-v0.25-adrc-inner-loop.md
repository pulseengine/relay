# v0.25 — ADRC inner loop: contains the instability, position-hold still bistable

Date: 2026-05-30. gz Harmonic, geo-hover scenario, `--home=…488`.

## What shipped (unit-tested, 4 tests)

`relay-adrc` — linear ADRC (Active Disturbance Rejection Control) per body
axis, the v0.24-finding fix: a 2nd-order extended-state observer (ESO)
estimates the body rate AND the lumped total disturbance (actuator lag,
effectiveness mismatch, rotor drag), and the control cancels it. Robust to
a wrong `b0` — the ESO absorbs the mismatch. Architecture: geometric outer
loop → desired body rate (`relay-geo::desired_rate`); ADRC inner loop →
torque.

Proven in unit tests:
- `adrc_tracks_through_actuator_lag_and_disturbance`: tracks Ω_d through a
  50 ms actuator lag + unknown disturbance + wrong b0 (4 vs assumed 6) —
  exactly the v0.24 failure mode.
- `eso_identifies_disturbance`, `regulates_rate_to_zero_under_disturbance`,
  totality proptest.

## gz result — real improvement, but bistable

| config | final_dist |
|---|---|
| direct torque + active yaw (v0.23) | 67 m (fly-off) |
| ADRC + default compass | ~3 m (contained) |
| ADRC + tight compass (YAWVAR 5e-4) | **0.48 m PASS** … but |
| ADRC + tight compass, 3 fresh runs | 3.04 m / 4.12 m / 28.82 m |

ADRC **contained the inner-loop actuator-lag instability** that flew the
body off (67 m → ~3 m typical), and *one* run with a tight compass closed
position-hold (0.48 m final, 0.39 m rms — the ±0.5/1.0 bar). But it is
**bistable** — 3 fresh runs gave 3.0 / 4.1 / 28.8 m. Not reliable.

## Honest status

This is the v0.19.7 bistability pattern again, and the discipline is the
same: **do not claim a reliable PASS from a lucky run.** ADRC is a real,
unit-validated improvement (the ESO does reject the actuator-lag
disturbance, and the body no longer flies off catastrophically). But the
**outer yaw loop is still marginally unstable** — the body rotates in yaw
rather than holding heading, and when the yaw/position coupling happens to
align, position holds (0.48 m); when it doesn't, it drifts (28 m).

The residual is the yaw *outer* loop, not the inner loop ADRC fixed:
- ADRC tracks the desired yaw RATE robustly (inner loop solved).
- The geometric desired_rate for yaw, driven by the (now-accurate) yaw
  estimate, still drives a slow continuous rotation instead of settling —
  the body never holds heading reliably.

Next (still v0.25 / into v0.26): make yaw HOLD, not just track-rate.
Candidates: the ADRC outer-yaw tuning (observer/control bandwidth), the
geometric yaw P-gain vs the weak yaw authority, or the ESO disturbance
estimate feeding the heading hold. This is the difference between
"contained + occasionally passes" and "reliably holds 4/4" — the bar v0.21
→v0.25 must clear before release.

## The exhaustive yaw-control matrix (all bistable; YAW_OFF most stable)

After ADRC contained the fly-off, I tried to make active yaw control
reliable. Every approach is bistable; only NO yaw control is stable:

| yaw approach | 3–4 fresh runs (final_dist) |
|---|---|
| direct geometric torque (k_R 0.15) | 67 m (fly-off) |
| ADRC rate-track, default compass | ~3 m typical |
| ADRC rate-track + tight compass | 0.48 / 3.0 / 4.1 / 28.8 m |
| gentle geometric (k_R 0.05) | 2.3 / 56.7 / 7.1 m |
| ADRC yaw RATE-HOLD (Ω_d,z=0) | 25 / 2.0 / 59 / 26 m |
| ADRC slow yaw (ω_o 8, ω_c 2) | 12 / 53 / 17 / 68 m |
| **YAW_OFF (no yaw torque)** | **stable, 1.22 m** (near-pass) |

Reframing: the frame-check oracle shows yaw authority is STRONG
(0.15 torque → 0.68 rad/s), not weak. So this is a **high-gain loop +
actuator (motor-speed) lag** → unstable-with-delay, and slowing the loop
did not rescue it. **Any** active yaw feedback closure destabilises;
open-loop yaw is stable. This is an open, research-grade issue — likely
the gz `MulticopterMotorModel` yaw actuator/drag dynamics interacting with
the closed yaw loop — not resolvable by gain tuning. It needs a dedicated
investigation (identify the gz yaw actuator response; possibly a different
yaw control structure, or it is partly a sim artifact).

## Honest bottom line for the v0.21→v0.25 arc

- The verified components are **all built and unit-tested**: relay-iekf
  (9), relay-geo (5), relay-adrc (4). The estimator, the geometric
  outer-attitude loop (no Euler coupling), and the ADRC inner-rate loop
  (rejects the actuator-lag disturbance) each work in isolation and in
  the gz cascade for roll/pitch/altitude/position.
- **Position-hold is NOT yet reliable.** It is bistable with any active
  yaw control and near-passing (1.22 m, altitude-offset-limited) with
  yaw control off. Two residual issues remain before release:
  1. the yaw control-loop instability (above) — the dominant blocker;
  2. an altitude steady-state offset (the alt loop wants an integrator).
- Per the v0.19.7 discipline: **not shipped as a reliable hover.** The
  arc is "built + characterised", and the release gate (reliable 4/4)
  is not met. The branch holds everything; nothing is released.

## Validated stack so far (all unit-tested)

- relay-iekf (9): full-state IEKF.
- relay-geo (5): geometric SE(3), no tilt-yaw coupling, Ψ→0.
- relay-adrc (4): ADRC inner loop, rejects actuator-lag disturbance.
gz: tilt perfect; inner-loop fly-off contained; position-hold demonstrated
(0.48 m) but bistable. Estimator + outer-attitude + inner-rate all work;
the yaw-HOLD outer loop is the remaining reliability gap.
