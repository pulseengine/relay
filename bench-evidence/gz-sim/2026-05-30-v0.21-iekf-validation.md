# v0.21 — Invariant EKF validation (Mahony vs IEKF in gz)

Date: 2026-05-30
Backend: Gazebo Harmonic, `--home=47.3977,8.5456,488`, `hover` scenario.
Branch: `falcon-v0.21-iekf` (WIP — NOT released; does not yet fly).

## The categorical result

The IEKF (relay-iekf) runs in the gz cascade fed IMU (propagate) + gz
NavSat position (update_position). Body is physically level
(`true_tilt` < 2° early). Attitude-estimate tilt, the quantity v0.20
showed the Mahony filter getting catastrophically wrong:

```
 t     true   Mahony    IEKF
 5.0   0.1°    3.3°      2.8°
 6.0   0.5°   25.7°      8.8°
 6.5   0.5°   48.7°     10.0°
 7.0   1.0°   95.8°      9.0°
 7.5   2.0°  140.8°     11.3°   (parallel run, control on Mahony)
```

The Mahony filter flips to **140°** (complete loss); the IEKF tracks
within **~10°**. Its position estimate tracks gz truth closely
(`ipos ≈ true pos` throughout). **140° → 10° is the keystone working.**

## Closing the loop on the IEKF

Switching the cascade's control attitude source to the IEKF (`USE_IEKF`):

- final_dist = **34.7 m** (vs the Mahony cascade's **206 m**) over 30 s.
- Trajectory: the IEKF tracks *excellently* at hover (t=0–2.5 s: IEKF
  tilt 0.0–0.7° vs true 0.1°; body climbs to −2 m and holds, pos ≈ 0),
  then a small attitude error (~3° at t=3 s) feeds the position
  controller → the body tilts → translates → attitude becomes less
  observable → error grows → drift.

## Tuning pass — smooth velocity + gentle gains

Feeding the IEKF's own (smooth) velocity to the position controller
(instead of noisy NavSat finite-diff) and gentling the position gains
(kp_pos 1.0→0.4, tilt_max 25°→11°) for the 2 kg body dramatically
improved the IEKF **tilt** tracking — it now stays within a degree of
truth for 15–20 s:

```
 t      true_tilt   IEKF_tilt
 5.0    0.0°        0.4°
 10.0   0.6°        1.4°
 15.0   0.7°        2.4°
```

## The decisive finding — yaw is unobservable (needs a magnetometer)

With tilt now excellent, adding IEKF **yaw** to the trace exposes the
real blocker. True yaw ≈ 0 (no yaw command), but the IEKF yaw estimate
swings wildly:

```
 t      true_tilt   IEKF_tilt   IEKF_yaw
 2.0    0.0°        0.0°         −0.5°
 5.0    0.0°        0.4°        −94.4°
 8.0    0.0°        0.7°        +24.5°
 14.0   0.3°        1.3°       −131.7°
 17.0   0.4°        0.6°        +90.3°
```

Roll/pitch are observable because **gravity anchors them** through the
dynamics; **yaw has no anchor** with IMU + GPS only at near-hover (no
sustained horizontal acceleration to triangulate heading). So yaw
wanders ±130°, the position controller's "hold north" is misaligned by
up to 130°, and the body slowly drifts (final_dist ~80 m at the gentle
gains — a slow wander, not a runaway).

This is a **structural** limitation, not a tuning failure — exactly why
PX4 EKF2 runs a multi-hypothesis yaw estimator (GSF) and fuses the
magnetometer. **v0.21 (IMU+GPS IEKF) cannot close position-hold without
yaw observability.** The roadmap's v0.22 (magnetometer + multi-hypothesis
yaw) is therefore not a separate nicety — it is the other half of making
the IEKF fly, and is the immediate next step.

## v0.22 work done — full-state IEKF + four real bug fixes

The IEKF is now a complete full-state filter (9 unit tests). Added:
- **`update_yaw`** (heading/compass) — H = e_z on δθ; makes yaw observable.
- **`update_gravity`** (adaptive accel-tilt) — fuses the accelerometer as
  a gravity reference for roll/pitch with variance INFLATED as |accel|
  deviates from g. The principled RC#3 resolution: use accel for tilt
  when static, distrust it under acceleration. Fixed the tilt-estimate
  error (3° → tip-over) that the IMU+GPS-only filter had.
- **`init_heading`** — one-time alignment to the first compass reading
  (a 90° startup mismatch otherwise kicked the controller into a spin).

Four real bugs surfaced + fixed along the way (each hidden until the
estimator was correct):
1. **relay-pos yaw frame bug** — it mapped NED accel→tilt without
   rotating into the body-heading frame, so "pitch to go north" only
   worked at yaw 0. Fixed: rotate the horizontal accel command by yaw.
   (A correctness fix to a verified crate; identity at yaw 0, so all
   existing tests still pass.)
2. **Heading source** — the OdometryPublisher leaves `pose.orientation`
   unset (zero); the true orientation is on the `/model/<m>/pose`
   `Pose_V` topic (tag 2). Switched the compass to that.
3. **ENU→NED yaw** — `ψ_ned = π/2 − ψ_enu` (body spawns facing East =
   NED yaw 90°), verified against the spawn reading.
4. **Startup yaw kick** — see `init_heading`.

## Honest status — the controller is now the ceiling, not the estimator

With all four fixed, the IEKF tilt is excellent (gravity update: 0–4°
vs true 0–8°), position tracks gz truth, and the compass reads correctly
(90.1° at spawn). But closed-loop position-hold still does not close
(~43 m): the **body yaws freely and the Euler PID cascade cannot hold
heading**. This is a *controller* limit, not an estimator one:

- The Euler attitude-setpoint construction (`euler_to_quaternion(roll,
  pitch, yaw)`) **couples tilt into yaw** once heading ≠ 0 — commanding a
  tilt in a yawed frame injects a spurious yaw-rate command.
- Quad **yaw authority is weak** (frame-check: +0.15 torque → 4.6 rad/s
  roll but only 0.68 rad/s yaw), so the coupling-induced yaw is hard to
  arrest.

This is exactly what **geometric SE(3) control (v0.23)** fixes — it works
directly on the rotation manifold with no Euler decomposition and no
tilt-yaw cross-coupling. The IEKF (v0.21) is complete and validated as a
full-state navigation filter; closing position-hold is now gated on the
v0.23 controller, not on the estimator. The loop has empirically
motivated its own next step.
