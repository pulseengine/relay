# The attitude "limit cycle" is ESO windup under mixer saturation (#270)

**Date:** 2026-09-23 · **Commit:** `e1d00be` + `RING_TRACE` · **Rig:** gz sim 8.15.0,
`worlds/falcon-quad.sdf` · **Refs:** #270, #398

## The correction that made this findable

#270 and my own earlier note both said "the gz plant hovers with an attitude
limit-cycle". **That is wrong, and the wrongness is the whole diagnosis.** The
plant is fine. Measured on the same world, same commit, same binary:

| settled hover | roll/pitch rate RMS | motor range | FDI gate shut |
|---|---|---|---|
| `--scenario=flightcore` (15–25 s) | **0.0014 rad/s** | 0.5809 – 0.5869 | ~0% |
| `--scenario=supervised-rotorout` (8–10 s) | **1.70 / 1.80 rad/s** | **0.12 ↔ 1.0000** | **96.8%** |

Three orders of magnitude apart. **The ring belongs to a path, not to the
plant** — and the two paths apply *identical* estimator/altitude tuning
(`set_pos_var(0.25)`, `set_process_floor(0.30,0.05)`,
`set_altitude_gains(0.15,1.00)`, `set_altitude_integral_gain(0.03)`) and the
same `hover_thrust = 0.585`.

(This also corrects the "gate shut 60% of ticks" figure I reported earlier from
a 25-tick sample. Over 500 ticks it is **96.8%**. The FDI gate is not chattering
at 60/40 — it is essentially always shut, with rare open windows. That is why
isolation succeeds occasionally rather than half the time.)

## The rate loop is not tracking

`RING_TRACE` logs the whole rate-loop slice per tick: measured gyro in, desired
body rate and commanded torque out, resulting motors.

| | commanded `omega_d` rms | measured gyro rms | tracking error |
|---|---|---|---|
| supervised (8–10 s) | 0.1443 rad/s | **2.4674 rad/s** | **2.5061 rad/s** |
| flightcore (15–25 s) | 0.0002 | 0.0019 | 0.0019 |

The attitude loop asks for ~0.14 rad/s. The vehicle does 2.5 — **17× the
command**, in the opposite phase. Commanded torque RMS is 0.62–0.68 against
0.0005 in the clean path.

So this is **not** a bad setpoint handed down from the attitude loop. The inner
rate loop is oscillating on its own, at **3.5 Hz**, with the motors railing
between 0.12 and 1.0000.

## Onset: it breaks during takeoff, as the motors first saturate

```
 t-window     gyro_rp_rms   torque_rms   motor_min  motor_max
 0.00-0.25       0.0019       0.0004      0.5759     0.8866     clean
 0.25-0.50       0.0232       0.0060      0.5536     0.6059     clean
 0.50-0.75       0.3324       0.1008      0.1300     0.9945     <-- saturation begins
 0.75-1.00       1.4320       0.5152      0.0588     1.0000     <-- ring established
 1.25-1.50       2.6356       0.9267      0.0991     1.0000
 …
 8.25-9.25       2.4800       0.9127      0.1215     1.0000     sustained, 7 s later
```

The ring appears **in the same window the motors first hit their limits**, and
never recovers. It is a sustained limit cycle, not a decaying transient.

## Mechanism — the ESO is lied to about what torque was applied

`relay-adrc`'s observer is driven by the input it *believes* was applied:

```rust
self.u_prev = u;                                        // the RAW computed control
self.u_act += dt * (self.u_prev - self.u_act) / tau;    // actuator LAG only
z1_next = z1 + dt * (z2 + b0 * self.u_act + beta1 * e); // ESO integrates this
z2_next = z2 + dt * (beta2 * e);                        // beta2 = omega_o^2 = 1600
```

The code comment states the correct principle — *"the ESO must be driven by the
torque actually DELIVERED, not the raw command"* — and implements it **for
actuator lag only**.

But the torque is also scaled by the mixer. `falcon-core` calls
`mixer.mix_thrust_floor(torque, thrust, 0.0)`, which is **thrust-priority
(MIX-P05)**: it computes the largest `s ∈ [0,1]` keeping every motor in range
and applies `base + s·d[i]`. The delivered torque is `s · torque`. **`s` is
computed inline, is not exposed, and is never fed back to the ADRC.**

So whenever the mixer saturates:

1. ADRC commands torque `u`; the vehicle receives `s·u`, `s < 1`.
2. The ESO integrates as if `u` had been applied, so `e = om − z1` grows.
3. `z2` (the disturbance estimate) integrates that error at `β2 = ω_o² = 1600`.
4. The control `u = (kp·(ω_d − z1) − z2) / b0` answers with *more* torque.
5. More torque ⇒ more scaling ⇒ a bigger lie. The loop latches into a
   rail-to-rail limit cycle that sustains its own saturation.

**This is integrator/observer windup with no anti-windup path**, and it explains
every observation: it starts exactly when saturation starts; it never recovers
once established; and `flightcore` is immune because it never saturates (motors
sit in a 0.006-wide band around 0.584, so `s ≡ 1` and the ESO is told the truth).

Thrust-priority also explains *why takeoff*: climbing uses collective, which
leaves the least torque headroom, so `s` is smallest exactly during takeoff.

## Consequences

- **#270 is misfiled as a plant/tuning issue.** Widening the FDI rate gate
  1→2 rad/s treated a symptom of this, and that workaround has now been
  consumed (the cycle grew from ~1 to ~2 rad/s).
- **#398 is downstream.** The FDI gate is shut 96.8% of supervised-hover ticks
  because of this cycle, so rotor-loss detectability is decided by which rare
  open window the failure lands in.
- The 19 `FlightSupervisor` takeoffs in the test suite all fly through this.

## NOT claimed

- That the fix is only anti-windup. **This hypothesis has not yet been tested by
  correcting it.** The evidence is correlational (onset coincides with
  saturation; the non-saturating path is clean; the mechanism is arithmetically
  consistent) but the decisive test is to feed the ESO the achieved torque and
  re-measure. Until that runs, this is a well-supported hypothesis, not a
  verified cause.
- Any claim about the real airframe. This is the gz plant.

## Falsification

Wrong if feeding the ADRC the mixer's applied torque scale (`s·u` instead of
`u`) leaves the supervised hover's roll/pitch rate RMS above ~0.1 rad/s, or if
a run with guaranteed headroom (no motor within 2% of a limit) still rings.
