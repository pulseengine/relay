# Rotor-out recovery does NOT hold on the gz plant (v1.140, #398)

**Date:** 2026-09-23 · **Commit:** `e1d00be` (main) · **Rig:** gz sim 8.15.0,
`worlds/falcon-quad.sdf`, macOS arm64 · **Cited by:** FV-FALCON-FAULT-005

## What was being established

FV-FALCON-FAULT-005 is the gz half of SWREQ-FALCON-FAULT-P02 — the last
engineering item in v1.140's scope. The mock half was tightened in #474 so the
verdict stops accepting a falling vehicle. This run asks the question that
matters: **does the same judgement pass on the real plant?**

It does not. **Four pristine-server trials, four FAILs.**

## The control — the rig is healthy

Run first, on the same server generation, so a rotor-out failure cannot be
confused with a bench that cannot fly:

```
./scripts/gz-trial.rs --label control -- ./target/release/falcon-sitl-gz \
    --backend=gazebo --scenario=flightcore --duration=25
```
```
verdict: scenario=flightcore target=2.0m final_dist=0.11m peak_dist=2.00m
         rms_steady=0.10m final_horiz=0.01m peak_horiz=0.02m est_z=-2.11m
PASS
```

A 2 m hold to 0.11 m with 1 cm of horizontal drift. The plant, the bridge and
the tuning are all working. Whatever follows is about the rotor loss.

## The measurement

```
./scripts/gz-trial.rs --label rotN -- ./target/release/falcon-sitl-gz \
    --backend=gazebo --scenario=supervised-rotorout --duration=25
```

Rotor 0 is killed at t=10.0 s of a 25 s flight. `peak_tilt_after` /
`peak_horiz_after` are measured **after** the loss; thresholds are the #474
ones (`isolated == Some(0)`, `peak_tilt_after < 0.5`, `peak_horiz_after < 10.0`,
landed, disarmed).

Every trial gets a **fresh server** via `gz-trial.rs` — the world never resets,
so trial N+1 on a live server starts wherever trial N left the airframe.

| trial | isolated | peak tilt after | peak horiz after | landed | disarmed | verdict |
|---|---|---|---|---|---|---|
| rot1 | **None** | **3.142 rad (180°)** | 9.55 m | no | no | FAIL |
| rot2 | Some(0) | 0.886 rad (50.8°) | 3.94 m | 11.148 s | yes | FAIL |
| rot3 | Some(0) | 0.867 rad (49.7°) | 8.38 m | 10.972 s | yes | FAIL |
| diag | Some(0) | 1.272 rad (72.9°) | 5.32 m | 11.000 s | yes | FAIL |

(A fifth run, on a contaminated server before the restart discipline was
applied, read `isolated=None`, 2.935 rad, 4.05 m. It is listed for completeness
and is **not** counted above — its start pose was not pristine.)

## What the numbers say

**Two distinct failure modes, from the same binary on the same world.**

1. **Total inversion (rot1).** The FDI never isolated the dead rotor
   (`isolated=None`) and the airframe reached 3.142 rad — exactly inverted. It
   never landed and never disarmed; it was still tumbling when the run ended.
   This is the `no tumble` clause of FAULT-P02 failing outright.

2. **Isolate-and-come-down (rot2/rot3/diag).** The FDI *did* isolate rotor 0,
   the motor failsafe commanded LAND, and the vehicle touched down and disarmed
   within ~1 s of the loss. But peak tilt after the loss is **0.87–1.27 rad
   (50–73°)**, against a 0.5 rad bar, and it travels **3.9–8.4 m** getting there.

**The run-to-run spread is the finding, not noise to average away.** Whether the
FDI isolates at all flips between runs of an unchanged binary against an
unchanged world. 1 of 4 clean trials never isolated. An intermittent FDI on a
safety property is worse than a consistently failing one, because a campaign
that samples it a few times can report success.

Note the near-miss: rot1's 9.55 m horizontal is **inside** the 10.0 m threshold.
Had it also isolated, that trial would have failed only on tilt. The horizontal
bar is not carrying much weight here and should not be read as validated.

## What this does NOT say

- **Nothing about the wasm cascade.** `--scenario=supervised-rotorout` drives
  the **native** `FlightSupervisor`. `main.rs` states plainly that *"the wasm
  cascade flies this same FlightCore with NONE of this tuning"* — and the gz
  branch of this scenario applies `set_pos_var` / `set_process_floor` /
  `set_altitude_gains` / `set_altitude_integral_gain` that the component does
  not receive. #398 was reported against the **wasm** cascade, so this
  measurement is adjacent to that report, not a reproduction of it. The wasm
  leg lives in `tests/cascade-sitl-wasm` (gazebo.yml), not in this binary.
- **Nothing about the cause.** No instrumented trace was taken. The FDI
  intermittency and the 50–73° excursion are *observations*; attributing them
  (allocator rank-deficiency behaviour, detection latency under real rotor
  dynamics, the tuning gap above) needs the `fdi_diag()` trace that
  FV-FALCON-FAULT-004 used, and that work is not done here.

## Consequence for the release

**FV-FALCON-FAULT-005 stays `proposed`.** The evidence required for `verified`
does not exist: the property does not hold on the plant it claims to hold on.
v1.140 therefore cannot reach 11/11 by measurement — only by a scope decision.

## Falsification

This finding is wrong if `--scenario=supervised-rotorout` on `--backend=gazebo`
produces `isolated=Some(0)` with `peak_tilt_after < 0.5` on three consecutive
pristine-server trials at this commit. It was not observed once in four.
