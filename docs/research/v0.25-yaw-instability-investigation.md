# Yaw-instability investigation — 3 parallel agents, convergent diagnosis

Date: 2026-05-30. Investigating: in the gz cascade, ANY active yaw
feedback makes position-hold bistable; open-loop yaw is stable; roll/pitch
rock-solid. Three subagents (gz-model physics, PX4/gz known-issues,
control-theory) investigated in parallel and CONVERGED.

## Root cause (convergent)

Closing a high-gain feedback loop around the **unmodeled motor-speed
actuator lag** on the **weakest, laggiest axis (yaw)**:

- **Yaw is the weak axis.** Yaw torque = differential rotor DRAG
  (`momentConstant=0.016`), not differential thrust. Per the gz SDF,
  `k_m/L = 0.016/0.0884 = 0.18` → for the same Δω, yaw makes only ~18% of
  the torque roll/pitch do → yaw needs ~5.5× more Δω, through the slow
  actuator. Yaw inertia is also ~1.8× (izz 0.040 vs ixx/iyy 0.0217).
- **The actuator lag.** Motor speed follows a first-order lag
  `timeConstantUp=0.0125 s`, `timeConstantDown=0.025 s` (spin-down 2×
  slower; yaw is a CW↑/CCW↓ push-pull so it eats the slow branch). Yaw's
  loop crossover `ω_c·τ ≈ 1` (vs ≪1 for roll/pitch) → ~45° phase-margin
  loss → closed-loop instability. Open-loop has no feedback path → the lag
  is benign → stable. Exactly the observed signature.
- **Throttle-dependent gain (a second, independent bug).** The bench
  mapped mixer-output→rotor-speed LINEARLY (`ω=pwm·1000`), but gz thrust
  is QUADRATIC (`∝ω²`), so actual thrust ∝ pwm² and the effective control
  gain `∂τ/∂pwm ∝ pwm` — throttle-dependent → conditional/bistable
  stability. (PX4/ArduPilot linearise this via `THR_MDL_FAC`/`MOT_THST_EXPO`.)
- **ADRC made it worse when slowed** because lowering ω_o slid the ESO
  below 1/τ; the ESO then mis-attributes the actuator lag to "disturbance"
  and cancels it destabilisingly. ADRC needs ω_o ≈ 3–10·ω_c AND the
  actuator lag IN the plant, not left unmodeled.
- The frame-yaw oracle already ruled out the swapped-sign / positive-
  feedback case (the #1 PX4-community suspect): +yaw torque → +yaw rate.

Agent verdict: a REAL flight-dynamics interaction gz reproduces
faithfully (not a sim bug, not a typo) — the textbook "weak axis + motor
lag + high loop gain" instability.

## Fixes applied

1. **√ PWM map** (`physics.rs`): `ω = √pwm · max` → thrust ∝ pwm (linear),
   gain throttle-invariant. Moved the hover point 0.72 → ~0.52.
2. **ADRC bandwidths** (yaw): ω_o=30 (high, below 1/τ≈40), ω_c=3 (control
   bw below the motor pole). Roll/pitch ω_o=40, ω_c=12.
3. **Actuator-lag model in the ESO** (`relay-adrc` `tau` field): drive the
   ESO with the DELIVERED torque (`b0·u_act`, u through a first-order τ
   filter) not the raw command — the INDI synchronisation move. yaw
   τ=0.025, roll/pitch τ=0.0125.

## Result — improved, NOT yet reliable

The actuator-lag model **eliminated most blowups**: runs went from
catastrophic divergence (100–500 m) to mostly-contained (1–4 m), with the
IEKF yaw tracking the compass within ~1° throughout. But it is **still
bistable** — an occasional run still yaws/drifts/blows up (e.g. 218 m).
The yaw control dynamics are improved but not fully stabilised.

## Remaining options (now fast to try via the config crate)

- **Yaw deprioritisation in the mixer** (PX4/ArduPilot: sacrifice yaw
  before roll/pitch/thrust on saturation; airmode) — the standard
  production answer, not yet implemented in `mix_thrust_floor`.
- **Higher-order ADRC** (estimate the actuator state explicitly) rather
  than the first-order-filter synchronisation approximation.
- **Motor-command low-pass / slew limit** (PX4 `CA_Rn_SLEW`) to further
  bandlimit below the motor pole.
- **PX4-SITL cross-check** to confirm the same controllers fly with active
  yaw outside gz (rule out a residual sim quirk).

All now sweepable in `configs/falcon-quad.json` WITHOUT a rebuild.
